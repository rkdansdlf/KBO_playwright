# PA 공식 기준선 (Season PA Baseline)

## 무엇을 위한 것인가

여름 PA 공식 위반은 **개수가 아니라 행**으로 봐야 한다. 위반 2,603건이 지금
있지만 전부 복구 불가능하다 — 출처 페이지가 robots.txt 에 막혀 있고, 해당 시즌의
경기 단위 행이 없어서 다시 유도할 수 없다. PA 공식(`PA = AB+BB+HBP+SH+SF`)으로
빈 값을 채우는 것은 야구 통계를 지어내는 일이다. 그래서 **기록만 한다.**

그래서 이 저장소는 두 가지를 잰다.

| 테이블 | 내용 | 매일 바뀌나 |
|---|---|---|
| `pa_violation_baseline` | 기록 시점에 이미 위반이던 (체크, 시즌, 선수) | 아니오 |
| `pa_unrecoverable` | 어떤 합법적 출처도 채울 수 없는 누락 카운트 | 예 (크롤러가 또 잃으면) |

점수는 `failure_count` 로 이미 깎인다. 백로그를 점수에 한 번 더 먹이지 않는 이유:
같은 신호를 두 번 빼면 매일 점수만 내려가고, 어느 쪽 때문에인지 구분할 수 없다.

## 왜 DB 인가

파일이었다. 이 저장소가 있는 머신에 파일이 생기고, 스케줄러가 도는 곳에는
없다. 근거는 측정했다.

- DB 의 마지막 크롤 런이 12분 전인데 이 머신의 `logs/scheduler.log` 는 그보다
  오래전(11:57 KST)부터 갱신되지 않았다.
- `logs/scheduler.launchd.err.log` 는 10월 4일에 멈춰 있다.

즉 크롤은 다른 호스트에서 돈다. 저장소 기준 경로의 파일은 daily 게이트가 영원히
읽지 못하고, 비교는 조용히 꺼진 채 "기준선이 없습니다" 만 반복한다.

## 기록하는 법

```bash
# 전체 시즌 (기본). 마이그레이션이 이미 돌았다면 이 한 줄이면 끝난다.
./venv/bin/python -m src.cli.data_quality_regression_pack --write-baseline
```

기록된 내용을 확인한다 (읽기 전용).

```sql
SELECT scope_season, count(*) FROM pa_violation_baseline GROUP BY 1 ORDER BY 1;
SELECT count(*) FROM pa_unrecoverable;
```

실측(2026-10-12): 45개 시즌 · 2,552행 / 복구불가 20행(8명).

**여기서 되돌리려면** 기록은 덮어쓴다. `DELETE` 후 재기록이라, 백로그가 실제로
줄어든 경우에도 그 상태가 그대로 반영된다. 지워지는 값은 없다.

## 시즌이 키의 일부인 이유

`scope_season` 은 "기록을 떼어낸 실행의 범위"가 아니라 **그 행이 발견된 시즌**이다.

780명 중 452명이 여러 시즌에 걸린다. 행에 시즌이 없으면, 2026 실행은 자신이 본
46명을 기록의 760명 안에서 찾고 나머지 **714명을 복구된 것으로 센다.** 실측으로
확인했다 — `baseline_available=False` 가 되고 신규 손상은 0건으로 아무것도
보고되지 않는다.

이 두 방향을 뮤테이션으로 검증했다. 쿼리에서 시즌 필터를 제거하는 변이, 비교에서
시즌 필터를 제거하는 변이, **둘 다 테스트를 그대로 통과했다.** 계약을 담는
테스트를 추가해 둘 다 잡히게 했다.

한 방향만 남는다 — 한 시즌 기록을 전체 실행이 읽는 경우. 이때 다른 시즌의 위반이
전부 신규 손상으로 보고되고 그 값이 점수에서 빠진다. 그래서 `is_scope_mismatch`
로 막는다.

## 판정이 조용한 경우 두 가지

1. **기록이 없다** → `baseline_available=False`. 빈 기록으로 읽으면 첫날에 전체
   2,603건이 신규 손상으로 보고된다. 값이 점수에서 빠지므로 조용히 틀린다.
2. **테이블이 없다** (마이그레이션 전) → 읽기는 "비교 안 함"으로 보고한다. 신축
   설치의 정상 상태라 예외를 던지지 않는다 — 던지면 품질 게이트 단계 전체가 죽는다.
   기록(write)만 `BaselineUnreadableError` 로 남는다. 여기서도 조용히 빈 기록을
   쓰면 전체가 신규로 보고되므로, 원인이 적힌 메시지를 던지는 편이 낫다.

`quality:daily` 인시던트는 **PASS 여도** 기준선 미기록이면 WARNING 으로 연다.
`resolve` 로 닫으면 "측정된 적이 없음"과 "측정했고 이상이 없음"이 같아져서
비교가 꺼진 채로 남는다.

## 검증

```bash
./venv/bin/python -m pytest \
    tests/test_data_quality_regression_pack_core.py \
    tests/cli/test_data_quality_regression_pack_cli.py \
    tests/services/test_quality_hub.py \
    tests/db/test_pa_violation_record_models.py \
    tests/sync/test_table_dag_registry_contract.py -q
```

`test_pa_violation_record_models.py` 는 마이그레이션이 만드는 컬럼 집합과 모델이
선언한 컬럼 집합을 비교한다. 둘이 어긋나도 아무 데서 실패하지 않는다 — 마이그레이션은
배포 때 한 번, ORM 메타데이터는 다른 무언가가 테이블을 만들 때만 조회되고, 첫 신호는
컬럼 없는 라이브 쿼리가 daily 게이트 안에서 터지는 것이다.
